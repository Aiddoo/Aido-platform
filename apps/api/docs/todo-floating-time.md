# 할 일 떠 있는 시각

할 일 시각 계산·시간대 재계산·리마인더 회차를 바꿀 때 읽는다. 한국에서 만든 오전 10시는 미국에서도 오전 10시이고 알림도 현지 10시에 울린다. 값의 의미와 시간대 규칙은 [날짜·시간·언어 5절](../../../docs/conventions/dates.md#5-떠-있는-시각)이 정본이고, 이 문서는 서버 구현과 운영을 적는다.

코드 정본은 `modules/planning/shared/domain/todo-calendar.domain-service.ts`(`resolveScheduledInstant`, Temporal), `todos/application/use-cases/resolve-todo-timezone.use-case.ts`, `todos/application/use-cases/rebase-todo-timezone.use-case.ts`, `todos/infrastructure/jobs/`다. 리마인더 예약·취소는 `todos/application/use-cases/apply-todo-events.use-case.ts`가 할 일 변경과 같은 트랜잭션에서 한다.

## 쓰기

모든 쓰기 경로는 벽시계(`HH:mm`)를 받는다. 출시 앱을 포함해 순간을 보내는 경로는 없다.

| 경로                                                 | 시각을 정하는 곳                                                                  |
| ---------------------------------------------------- | --------------------------------------------------------------------------------- |
| `POST /v1/todos`, 메모 변환, 계획 적용, AI 제안 수락 | `StagedTodoCreatorPort.stage`(`StageTodoCreationUseCase`) → `TodoSchedule.create` |
| `POST /v1/todos/recurring`, 회차 채우기              | `TodoSeries`의 회차 초안                                                          |
| `PATCH /v1/todos/:id`(시간·날짜)                     | `Todo.updateDetails` → `TodoSchedule.patch`                                       |
| `PATCH /v1/todos/:id/schedule`                       | `TodoSchedule.create`                                                             |
| 이후 모두·규칙 변경·반복 전환                        | `UpdateFollowingTodos`, `StartSeriesFromTodo`의 `resolveScheduledInstant`         |

날짜·시간을 건드리지 않는 수정(제목·공개·카테고리)과 완료·완료 되돌리기는 순간을 바꾸지 않는다. 순간은 재계산이 맞춘다. 완료를 되돌리면 지금 순간으로 알림만 다시 잡는다.

## 시간대 변경

규칙은 하나다. **시간 있는 모든 할 일의 `scheduledTime`은 `startDate + scheduledLocalTime + 사용자 현재 시간대`다.** 완료했거나 지난 할 일도 예외가 아니다. 그래서 출시 앱이 순간을 기기 시간대로 바꿔 보여 줘도 지난 할 일까지 고른 시각으로 보인다.

```text
앱 요청 → 저장값 변경(자가 치유·토큰 등록·설정 변경) ─ 같은 트랜잭션 → todo-timezone-rebase.v1
                                                         60초 구간당 사용자당 하나, 구간이 끝난 뒤 시작
worker → 규칙 시간대 변경 → 500행씩: 잠금 → 최신 시간대 확인 → 행 잠금·읽기 → 순간 다시 계산 → 완료 전이고 앞으로 울릴 회차만 알림 재예약 → 커밋
```

- **기준**: 앱을 앞에 띄운 기기의 마지막 요청이다. 새 칸 없이 `X-Timezone`을 그대로 쓴다. 기기 두 대가 번갈아 요청하면 저장값은 마지막 요청의 값이고, 작업은 구간당 하나이며, 작업은 실행 때 저장값을 읽으므로 결과는 마지막 값이다(`todo-timezone-rebase.integration-spec.ts`의 기기 두 대 표).
- **앱이 보내는 때**: 앱 시작, 복귀(`AppState active`), 푸시 탭, 앞에 떠 있는 동안 시간대 변경. 요청이 없는 화면이어도 푸시 기기 보고(`PUT /v1/notifications/push-devices/:deviceId`)가 나간다. 새 엔드포인트는 없다.

- **이벤트가 아니라 같은 트랜잭션에서 넣는다.** 도메인 이벤트는 재시도가 없어 커밋 뒤 프로세스가 죽으면 변경을 영영 놓친다. 저장값이 바뀐 뒤에는 다음 요청도 "변경 없음"이라 복구할 기회가 없다. 작업 등록이 실패하면 시간대 변경도 되돌아가고 다음 요청이 다시 시도한다.
- **구간 작업**: 작업 key에 60초 구간을 넣고 구간이 끝난 뒤 시작한다. 그 구간의 어떤 변경도 작업 시작 전이므로 놓치지 않고, 실행 중에 온 변경은 다음 구간의 새 작업이 된다. 기기 두 대가 번갈아 요청해도 사용자당 1분에 한 번이다.
- **멱등**: 벽시계에서 계산하므로 몇 번을 돌아도 같다. 순간이 그대로면 쓰지 않아 재시도는 남은 행만 바꾼다.
- **시각이 같은 시간대 전환**(서울 ↔ 도쿄): 작업은 돌지만(`scanned` N / `rebased` 0) `UserPreference.timezone`과 규칙의 시간대만 바뀐다. `Todo.scheduledTime`과 `todo-reminder.v1` 예약은 그대로이고 새 예약도 없다.
- **동시성**: 잠금 순서는 `todoCategory → todoSortOrder → 규칙 행 → 할 일 행`이다(카테고리 삭제·회차 채우기·이후 모두와 같다). 할 일 행은 `FOR UPDATE`로 읽어 단건 수정과 겹쳐도 최신 벽시계로 계산한다. 시간대가 또 바뀌었으면 남은 묶음을 멈추고(`SUPERSEDED`) 다음 작업이 끝까지 계산한다.
- **재예약**: 행과 함께 커밋한다. 완료 전이고 옛 시각이나 새 시각이 앞으로인 회차만 예약을 건드린다. 지난 이력에는 예약 요청을 보내지 않는다. 이미 지난 단계는 건너뛴다(아래). 이미 울린 단계는 아래 회차 규칙으로 다시 울리지 않는다. 서쪽으로 가서 시각이 다시 미래가 되어도 같다.
- **규모**: 사용자 전체 이력 5만 행(앞으로 2,700행 + 지난 47,300행, 예약 5,400개) 4.3~4.6초·SQL 622문장·힙 증가 73MB 이하, 다른 사용자 20만 행이 함께 있어도 같다. 바뀔 것이 없는 재실행은 3.2~3.7초·510문장이다. 규칙 30개 × 90일(2,700행) 0.35초·53문장·힙 증가 61MB 이하, 옛 경로 상한 300개 × 90일(27,000행) 3.4~3.6초·442문장·힙 증가 56MB 이하(로컬 Testcontainers 2회, `test/performance/todo-timezone-rebase.performance-spec.ts`). 문장 수는 행 수가 아니라 묶음 수를 따른다(예약 있는 묶음 8문장, 지난 이력만 있는 묶음 5문장). 새 색인은 없다. id 커서라 기본 키 스캔이 표 전체를 많아야 한 번 지난다.

## 알림 중복 방지

한 번 울린 단계를 막는 곳은 `Notification_todo_reminder_occurrence_dedup` 유니크 인덱스(할 일 + 단계 + 회차) 하나다. 회차(`Notification.reminderOccurrenceKey`)는 발송할 때 할 일의 `startDate`와 `scheduledLocalTime`으로 만든다(`createReminderOccurrenceKey`, 예: `2026-11-05T10:00`). 중복이면 발행이 `null`을 돌려주고 작업은 `ALREADY_NOTIFIED`로 끝난다.

재계산은 날짜와 벽시계를 바꾸지 않으므로 회차가 그대로이고, 사용자가 날짜나 시간을 고치면 회차가 달라진다. 그래서 시간대 재계산과 직접 수정을 따로 표시하지 않아도 구분된다.

| 일어난 일                            | 회차        | 이미 울린 단계                      |
| ------------------------------------ | ----------- | ----------------------------------- |
| 시간대 왕복·서쪽 이동·서머타임       | 그대로      | 다시 울리지 않는다                  |
| 작업 재시도·동시 처리                | 그대로      | 다시 울리지 않는다                  |
| 날짜 이동                            | 달라진다    | 새 날짜에 다시 울린다               |
| 같은 날 시간 변경(앞·뒤)             | 달라진다    | 새 시각 기준으로 다시 울린다        |
| 시간이나 날짜를 옮겼다가 되돌림      | 처음 회차   | 그 회차에 울린 단계는 울리지 않는다 |
| 종일로 바꿨다가 같은 시각으로 되돌림 | 처음 회차   | 그 회차에 울린 단계는 울리지 않는다 |
| 완료를 되돌림                        | 그대로      | 다시 울리지 않는다                  |
| 반복 회차                            | 행마다 따로 | 회차끼리 서로 막지 않는다           |

같은 날 시간을 고치면 다시 울리는 이유: 10시 할 일의 60분 전 알림을 받고 15시로 옮긴 사람은 14시에 알림을 기대한다. 날짜만 키에 넣으면 이 알림이 사라지는데, 고치려는 결함과 같은 모양이다.

회차는 응답과 푸시에 싣지 않는다. `metadata`는 앱이 받던 모양 그대로다. 예약 작업의 내용과 key(`reminder_<todoId>_<단계>`)도 그대로다. 다시 예약할 때는 먼저 지우므로 끝난 작업 행이 새 예약을 막지 않는다.

- **회차가 빈 옛 행**: 회차 칸이 생기기 전에 울린 알림은 대부분 회차가 비어 있다. 빈 값끼리는 인덱스가 할 일 + 단계로 막고, 새 회차를 막지 않는다. 휴면 안내(`series-paused`)도 빈 회차로 할 일마다 하나다.

## 지난 단계는 건너뛴다

`planReminderJobs`는 리드 타임을 빼도 앞으로인 단계만 예약한다(60분·10분). 이미 지난 단계를 바로 보내지 않는다. 바로 보내면 정시 직전에 시간을 고칠 때마다, 시간대를 건널 때마다 알림이 쌓인다.

| 남은 시간 | 예약       |
| --------- | ---------- |
| 60분 초과 | 60분, 10분 |
| 10분~60분 | 10분       |
| 10분 이하 | 없음       |
| 이미 지남 | 없음       |

만들 때도, 시간을 고칠 때도, 재계산 때도 같다. 그래서 5분 뒤로 만든 할 일에는 알림이 없다.

## 순간을 읽는 곳

| 곳                                             | 쓰임                                 | 범위를 넓힌 영향                                                 |
| ---------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| 리마인드 예약                                  | 지연 작업 시각                       | 없음. 완료 전이고 앞으로인 회차만 예약한다                       |
| 날씨 아침 푸시 `WeatherBriefingTodoReaderPort` | 오늘 남은 시간의 할 일 + 예보 맞추기 | 없음. 완료 전·지금 이후만 읽고, 같은 저장 시간대로 계산한 값이다 |
| 응답 `scheduledTime`(소유자·친구·댓글)         | 출시 앱 표시                         | 좋아진다. 지난 할 일도 새 시간대에서 고른 시각으로 보인다        |
| AI 제안 기록 `DrizzleSuggestionActivityReader` | 벽시계가 빈 옛 행의 대체값           | 없음. 벽시계가 있으면 그것을 쓴다                                |

리포트·통계·연속 기록·달성은 `startDate`와 `completedAt`을 쓰고, 목록 정렬은 `sortOrder`다. `scheduledTime`을 읽지 않는다.

## 관측과 실패

- 완료 로그 `planning.todo.timezone-rebase.completed`: `outcome`(`COMPLETED`·`SUPERSEDED`·`NO_PREFERENCE`), `scannedCount`, `rebasedCount`, `skippedCount`, `seriesCount`, `timezone`, `durationMs`. 제목은 남기지 않는다.
- 시도별 실패 `planning.todo.timezone-rebase.failed`. pg-boss가 3번 다시 시도하고(30초, 백오프) 마지막 시도까지 실패하면 경보 `planning.todo-timezone-rebase-failed`가 오른다. 이때 그 사용자의 알림은 옛 시각이다. 표시는 벽시계라 맞다.
- 개발·스테이징 `/health`의 job 상태에 `todo-timezone-rebase.v1` 대기·실행·실패 수가 보인다(운영 공개 응답은 상태만 준다).
- 탈퇴·설정 없는 사용자는 `NO_PREFERENCE`로 조용히 끝난다. 정지·휴면 사용자도 그대로 계산하고 발송은 기존 리마인더 처리가 건너뛴다.

## 한계

- **앱을 열기 전 도착**: 서버는 앱 요청 전까지 시간대를 모른다. 내려서 앱을 열 때까지 알림은 옛 시간대로 울린다. 푸시 수신만으로는 앱 코드가 돌지 않아 앞당길 수 없다. 앱을 열면 다음 구간(최대 약 1~2분) 안에 맞는다.
- **백그라운드 보고를 넣지 않은 이유**: `expo-background-task`는 실행 시점이 OS 재량이고 강제 종료 뒤에는 돌지 않아 도착 직후를 풀지 못하는데, 새 네이티브 의존성·백그라운드 모드·심사 설명이 늘고, 집에 둔 태블릿이 시간대를 되돌리는 위험도 생긴다.
- **기기 예약(로컬 알림)을 고르지 않은 이유**: 시간대 문제는 풀리지만 iOS 대기 64개 제한, 기기 여러 대 중복, 로그아웃·삭제 동기화, 옛 앱 공존 비용이 크다.
- **집에 둔 기기**: 다른 시간대의 기기를 앞에 띄우면 그 기기가 기준이 된다. 그 시간대로 알림이 옮겨 가고 원래 기기를 다시 띄우면 돌아온다.
- 날씨 푸시 문구는 순간을 알림 시간대로 적는다. 재계산 뒤에는 벽시계와 같다. 서머타임으로 없는 시각(뉴욕 02:30)만 전환 뒤 시각(03:30)으로 적힌다.
- 재계산 전 잠깐(최대 약 1~2분) 출시 앱에는 옛 시간대의 순간이 보인다. 새 앱은 벽시계를 보여 주므로 어긋나지 않는다.
