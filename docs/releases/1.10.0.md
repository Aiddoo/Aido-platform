이 문서는 2026-10-01에 시작한 1.10.0 변경의 결정, 구현, Before/After 근거와 배포 전 검증을 기록한다. 기준 커밋은 `c1c58408`, 기준 상태 수집 시각은 **2026-10-01 19:53:29 KST**다. 진행 중이던 앱 버전 확인·스토어 리뷰 작업을 포함한 상태를 보존하고 그 위에 변경을 이어갔다.

사용자 요청의 목표 버전은 1.10.0이다. 실제 수집한 모바일 기준 버전은 이미 1.9.1이었으므로 아래 비교는 **1.9.1 → 1.10.0**을 사용한다. API와 루트의 비공개 workspace package 버전은 모바일 배포 버전과 별개다.

## 1. 변경 범위와 채택 기준

### 기존 서버 롤백을 위한 pg-boss 예외

최신 라이브러리라는 이유만으로 작업 큐 schema를 변경하면 기존 앱 HTTP 계약을 유지해도 서버 교체가 안전하지 않다. PostgreSQL 16의 별도 임시 DB에서 다음 순서를 실제 실행했다.

| 실행                                                    | 결과                                        |
| ------------------------------------------------------- | ------------------------------------------- |
| pg-boss 12.27 시작, schema 37, 작업 send/fetch/complete | 통과                                        |
| 12.35 CLI로 schema 37 → 43 migration                    | 통과                                        |
| pg-boss 12.35 새 instance 시작                          | 통과                                        |
| pg-boss 12.27 기존 이미지 재시작                        | `pg-boss database requires migrations` 실패 |

이미 실행 중인 구 instance의 일부 기본 작업이 계속 성공하는 것과 구 이미지 재시작·롤백이 가능한 것은 다르다. 따라서 이번 릴리스는 **12.27.0을 유지하고 큐 schema migration을 만들지 않는다**. 12.28~12.35도 schema 38~43으로 올라가므로 중간 버전 선택으로 해결되지 않는다. API 전체 코드를 실제 12.27 declarations로 typecheck했고 현재 사용하는 metadata, transaction DB, cancellation, health count API가 제공되는 것을 확인했다.

이 검증에서 운영 DB는 접근하지 않았다. 이번 작업 중 schema 43이 이미 생성된 격리 개발 DB에서는 비즈니스 데이터와 기존 schema를 보존하고 검증 전용 schema 37을 새로 사용한다. 운영의 schema 37을 삭제하거나 임의로 version 값을 되돌리는 절차는 포함하지 않는다.

근거: [12.27 schema 버전](https://github.com/timgit/pg-boss/blob/12.27.0/package.json), [instance 시작 시 schema 검사](https://github.com/timgit/pg-boss/blob/12.27.0/src/contractor.ts), [12.35.1 릴리스](https://github.com/timgit/pg-boss/releases/tag/12.35.1), [공식 CLI](https://pgboss.io/cli). 재현 로그는 `/tmp/aido-pgboss-compat-audit.log`다.

## 2. 서버: ESM과 native Standard Schema

### 모듈과 실행 경계

| Before                                                | After                                                             |
| ----------------------------------------------------- | ----------------------------------------------------------------- |
| CommonJS 빌드와 런타임 alias 보정                     | package `type: module`, TypeScript NodeNext, Node package imports |
| 확장자 없는 상대 import                               | 출력 JS에서 해석 가능한 상대 `.js` import                         |
| 앱 초기화와 instrumentation import가 같은 main에 있음 | bootstrap에서 instrumentation을 먼저 평가한 뒤 main을 동적 import |
| 공유 package 소비 방식이 CJS 중심                     | validators/errors ESM export와 declaration 경계 정렬              |
| 앱 entrypoint와 Docker entrypoint를 별도로 추측       | `node dist/src/bootstrap.js`로 실행 경로 일치                     |

이전 bootstrap의 핵심 부분:

```ts
import './instrument';
import './shared/domain/date/dayjs.setup';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
```

변경 후 `apps/api/src/bootstrap.ts`:

```ts
import './instrument.js';

await import('./main.js');
```

`apps/api/package.json`의 런타임·타입 alias 경계:

```json
{
  "type": "module",
  "imports": {
    "#api/*": {
      "types": "./src/*.ts",
      "default": "./dist/src/*.js"
    },
    "#test/*": "./test/*.ts"
  }
}
```

Sentry instrumentation이 Nest 모듈보다 먼저 실행되어야 하는 순서를 유지한다. 기존 Pino logger, request identity, 오류 filter와 응답 interceptor를 새로운 추상화로 교체하지 않는다. 런타임과 HTTP E2E는 `configureApplication`을 공유하므로 prefix, CORS, helmet과 validation 설정이 서로 달라지지 않는다.

### 요청 schema와 REST 호환성

이전 `CreateTodoDto`:

```ts
import { createTodoSchema } from '@aido/validators';
import { createZodDto } from 'nestjs-zod';

export class CreateTodoDto extends createZodDto(createTodoSchema) {}
```

변경 후:

```ts
import { createTodoSchema } from '@aido/validators';
import type { z } from 'zod';

export const CreateTodoDto = createTodoSchema.meta({ id: 'CreateTodoDto' });
export type CreateTodoDto = z.infer<typeof CreateTodoDto>;
```

각 controller는 `@Body({ schema: ... })`, `@Query({ schema: ... })`, `@Param({ schema: ... })`에 공유 입력 schema를 연결한다. 예를 들어 기존 resource-limit 조회는 다음 계약을 갖는다.

```ts
async getResourceLimit(
  @CurrentUser() user: CurrentUserPayload,
  @Query({ schema: TodoResourceLimitQueryDto }) query: TodoResourceLimitQueryDto,
): Promise<TodoResourceLimitResponseDto> {
  return this.getTodoResourceLimitUseCase.execute({
    userId: user.userId,
    categoryId: query.categoryId,
  });
}
```

공통 입력 검증의 핵심:

```ts
app.useGlobalPipes(
  new StandardSchemaValidationPipe({
    exceptionFactory: (issues) =>
      new BadRequestException({
        statusCode: 400,
        message: 'Validation failed',
        errors: issues,
      }),
  }),
);
app.setGlobalPrefix('v1', { exclude: ['health'] });
```

DTO의 런타임 연결은 native pipe가 담당하고 데이터 shape의 원본은 `@aido/validators`가 담당한다. 요청 schema를 API와 앱에서 다시 정의하지 않는다. 공통 ErrorCode와 기존 성공/오류 응답 envelope를 유지한다. 제거한 `nestjs-zod` 역할 중 Swagger 변환은 별도 작은 converter가 맡는다.

OpenAPI converter는 Zod의 `z.toJSONSchema(schema, { io: "input" })`를 사용하고 nullable, 숫자 경계, const, `$ref`, component metadata를 기존 공개 문서 표현과 맞춘다. 입력 schema의 변환과 응답의 기존 표현을 구분한다. Zod 4.6을 적용했을 때 이미 공개한 schema fingerprint가 달라졌으므로 4.3.6을 유지했다. 최신화를 위해 외부 계약이 바뀌는 것을 허용하지 않았다.

OpenAPI snapshot의 실제 변경량은 **298 additions / 49 deletions**다. 이 줄 수는 snapshot의 새 endpoint·명시적 검증 정보 등을 포함한 문서 변경량이며 breaking endpoint 수가 아니다. 기존 배포 계약 hash는 변경하지 않았고 해당 계약 검사를 통과했다. snapshot 전체를 새 값으로 덮어 기존 호환성 실패를 숨기지 않는다.

## 3. 클라이언트: 예측 가능한 데이터·폼·컴포넌트

Moyeo 프론트엔드 문서의 의도는 적용하되 웹 전용 loader나 SSR 구조를 복제하지 않았다. 앱의 route는 Expo Router, 서버 상태는 TanStack Query, 폼 상태는 부모 React Hook Form이 소유한다. 상세한 feature별 기록과 예제는 [클라이언트 1.10.0 변경 문서](../../apps/mobile/docs/releases/1.10.0-client.md)를 참고한다.

### HTTP → wire schema → mapper → client model

| Before                                                | After                                                                         | 유지하는 계약                                    |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------ |
| `get<Response>()`가 실제 JSON을 런타임 검증 없이 신뢰 | HTTP는 `Result<unknown, ApiError>`, 전체 공유 응답 schema 검증 후 mapper 적용 | REST endpoint, 공통 오류 코드, 인증 refresh 흐름 |
| 일부 feature model이 응답 alias/Omit                  | 화면·정책에 필요한 독립 client schema/model                                   | 공유 vocabulary와 입력/응답 schema 재사용        |
| 서버 Date 문자열이 UI까지 전달될 수 있음              | mapper에서 검증된 문자열을 client Date로 변환                                 | 기존 API wire 형식                               |
| GET 취소 전달이 부분적                                | 모든 HTTP GET과 공개 설정 fetch가 AbortSignal 전달                            | 기존 query key·cache invalidation prefix         |

컴파일 타입만으로 외부 입력을 신뢰하지 않는다. 성공 envelope도 `success`, `data`, `timestamp`를 검증한 뒤 소비한다. 알 수 없는 error code, 잘못된 payload와 네트워크 실패는 기존 오류 채널로 처리한다. `unknown`을 `as Response`로 바꾸는 우회는 제거한다.

클라이언트 model의 독립성은 서버 응답 schema 복제와 다르다. 공유 schema가 전송 데이터를 검증하고, feature model은 앱이 사용하는 Date·필드·정책을 표현한다. 서버 응답이 확장되어도 화면 props와 정책이 자동으로 확장되지 않도록 mapper가 변경 경계를 만든다.

### Expo Router와 순수 조회 옵션

이전에는 queryFn이 DI hook 내부에 묶여 있었다. 변경 후 순수 factory에 service와 query dependency를 명시하고 기존 호출자를 위해 얇은 DI hook을 유지한다.

```ts
export function getTodosByDateQueryOptions(todoService: TodoService, { date }: { date: string }) {
  return queryOptions({
    queryKey: TODO_QUERY_KEYS.listByDate(date),
    queryFn: async ({ signal }) =>
      unwrap(await todoService.getTodos({ startDate: date, endDate: date, size: 200 }, signal)),
    placeholderData: keepPreviousData,
  });
}

export function useGetTodosByDateQueryOptions(date: string) {
  return getTodosByDateQueryOptions(useTodoService(), { date });
}
```

기존 함수형 API를 유지하면서 factory를 독립적으로 테스트할 수 있다. query key에 영향을 주는 값은 이름 있는 dependency로 전달한다. route ID는 지역 Expo Router hook에서 string/array 여부, 숫자 범위, CUID 등 실제 feature 계약을 검증한 뒤 사용한다. 잘못된 deep link가 API 요청을 먼저 발생시키지 않는다. WebView도 URL 검증을 하고 기존 인코딩 URL은 필요한 경우에만 decode한다.

Todo 화면의 preference·category·current-user·todos 네 조회는 `useSuspenseQueries`로 함께 시작한다. 조회 결과 조합은 순수 view-model 함수가 담당한다. query cache에는 서버 조회 결과를 유지하고 locale·표시 정책·category 조합은 projection에 전달한다. 같은 데이터를 받기 위한 새 provider나 중복 요청을 만들지 않는다.

### 부모 폼과 controlled 입력

| 책임                              | 소유 위치                                          |
| --------------------------------- | -------------------------------------------------- |
| 값·validation·제출 Promise        | 화면/폼 부모의 FormProvider                        |
| RHF Controller 연결               | shared FormField 한 곳                             |
| 필드 값·오류 구독                 | FormField fieldState, 필요한 useWatch/useFormState |
| native TextInput 이벤트 변환      | shared Input/TextArea 내부                         |
| 업무별 suffix·의미 있는 입력 확장 | feature 지역 입력 컴포넌트                         |

```tsx
<FormProvider {...form}>
  <FormField control={form.control} name="email">
    {({ value, onChange, onBlur }, { error }) => (
      <Input value={value} onChange={onChange} onBlur={onBlur} isInvalid={error != null} />
    )}
  </FormField>
</FormProvider>
```

Input의 공개 계약은 `value/onChange`이고 내부 native adapter만 `onChangeText={onChange}`를 사용한다. native의 focus/blur·ref 타입은 React Native 0.88의 원본 타입에서 가져온다. 공통 Input을 쓰는 것만으로 충분한 사용처에는 이름만 바꾼 wrapper를 추가하지 않는다. 금액 suffix 등 의미가 추가되는 입력만 AmountInput 같은 지역 컴포넌트로 표현한다.

Checkbox 확장은 `ComponentProps<typeof Original>`에서 wrapper가 소유하는 필드만 Omit하고 HeroUI 원본 `isSelected/onSelectedChange`를 유지한다. 라이브러리마다 다른 checked 계약을 임의의 공통 prop으로 다시 정의하지 않는다. 접근성·style·testID 등 원본 확장 지점을 전달한다.

제출은 `await mutateAsync`로 실제 작업 종료까지 부모의 제출 상태를 유지한다. 예상 가능한 업무 오류는 기존 toast/dialog에서, 예상하지 못한 오류는 ErrorBoundary에서 처리한다. 여러 단계 비밀번호 흐름은 같은 form session을 유지하고 전체 errors 또는 전체 form 값을 불필요하게 구독하지 않는다. 메모 저장·뒤로가기 자동 저장도 비동기 완료 순서를 유지한다.

### 종속 컴포넌트와 화면 조립

ProductList 예시의 의도에 맞춰 목록 없이는 의미가 없는 행·상태는 소유 컴포넌트와 같은 파일에 둔다. TodoList.Item, UserList.Item과 SuggestionsList.Item/Empty가 이 원칙을 적용한다. Loading/Error/Empty는 실제 기존 경계에서 필요한 경우 소유 컴포넌트의 namespace에 둔다. 모든 컴포넌트에 사용하지 않는 상태 API를 기계적으로 추가하지 않는다.

서버가 제공한 실제 컬렉션은 map으로 표현한다. 의미가 서로 다른 고정 결과는 ReportDetailContent의 명시적 JSX로 조립하고 공통 디자인만 지역 Section으로 공유한다. 하나의 섹션만 달라지는 변경이 전체 옵션 배열·조건문을 고치게 만들지 않는다. 다른 곳에서 쓰지 않는 지역 컴포넌트를 무조건 별도 폴더·파일로 분리하지 않는다.

Feed/Memo/Friend 화면이 Box 등의 기존 layout을 통해 바깥 간격을 소유한다. 목록·로딩 컴포넌트가 페이지 outer padding을 알아야 하는 구조를 정리한다. 행·card 자체의 디자인 간격은 해당 컴포넌트 안에 남긴다. 기존 shared/ui, bottom sheet, error boundary, DI와 저장소를 재사용한다.

### 순수 함수와 Policy facade

정책 함수는 먼저 명시적인 입력을 받아 순수 계산을 수행하고 Policy는 그 함수를 노출한다. `this`에 의존한 내부 호출, 순환 Policy 참조와 숨은 시간 의존성을 제거한다. `is/can/has/should` 함수는 boolean 판정으로 끝내고 금액·통계 계산은 반환 값이 드러나는 이름을 사용한다.

실제 SubTodo 정책의 좁은 입력 경계:

```ts
export function canAddSubTodo(parentTodo: { subTodoStats: SubTodoStats }): boolean {
  return !isMaxSubTodosReached(parentTodo.subTodoStats);
}

export function getStatsAfterSubTodoAdd(parentTodo: { subTodoStats: SubTodoStats }): SubTodoStats {
  return statsAfterAdd(parentTodo.subTodoStats);
}

export const SubTodoPolicy = {
  canAddSubTodo,
  statsAfterAdd: getStatsAfterSubTodoAdd,
} as const;
```

이 예제는 실제 facade의 일부다. 전체 TodoItem을 SubTodo model에 import하지 않고 필요한 stats만 받도록 바꾸어 Todo → SubTodo 의존성을 한 방향으로 만들었다. 삭제 정책만 readonly subTodos를 추가로 받는다. 새 공통 model이나 타입 단정으로 순환을 숨기지 않았다.

ts-pattern은 의미 있는 상태 분기를 exhaustive하게 표현하고 es-toolkit은 기존 유틸리티가 해결하는 작업에 사용한다. 단순 코드를 라이브러리 호출로 모두 바꾸거나 내부 wrapper를 다시 만들지 않는다. 공유 feature dependency는 공통 기반을 향하고 shared가 feature를 역참조하지 않도록 검사했다.

### 날짜·정리·가독성

날짜 표시에는 locale/timeZone이 명시적인 Intl 순수 함수를 사용한다. formatter cache는 최대 32개로 제한하고 자정은 h23로 표시한다. dayjs는 날짜 산술과 기존 YYYY-MM-DD API key에 유지한다. Expo 앱을 요청별 SSR 앱으로 가정하지 않으며 서버/앱 간 날짜 경계와 사용자 timezone이 예측 가능하도록 한다. 현재 날짜가 필요한 정책에는 기존 LocalDateProvider의 useToday/useTodayKey를 사용한다.

알림 debounce는 logout/unmount에서 취소하고 cooldown은 cleanup 가능한 일회성 timeout으로 예약한다. feature discovery의 idle 작업도 SDK 변경에 맞게 취소 가능한 requestIdleCallback으로 옮겼다. 불필요한 date plugin, wrapper, 구분선 주석과 코드가 그대로 설명하는 주석을 제거하고 공개 계약·호환 제약 등 중요한 이유만 남긴다.

파일명은 component PascalCase, hook/query/utils kebab-case, schema 변수 camelCase로 맞춘다. feature는 `models/services/presentations/{components,queries,hooks,schemas,view-models,utils,constants}`의 책임 구조를 공유하지만 필요한 파일이 없는 빈 계층은 만들지 않는다.

## 4. 홈 위젯과 시스템 탭

### 위젯 Before → After

| Before                                                      | After                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Android 전용 legacy renderer/service와 iOS 구현의 별도 관리 | expo-widgets 기반의 양 플랫폼 gateway·renderer·snapshot 경계                    |
| 플랫폼별 갱신 경로가 중복될 수 있음                         | 기존 DI/logging을 통한 하나의 갱신 책임과 직렬화된 update queue                 |

| 렌더러가 앱 문맥을 참조하기 쉬움                            | 작은 직렬화 가능한 snapshot과 isolated widget 함수                              |
| Android 기존 launcher 등록·코드 유지                        | 최소 legacy receiver identity만 유지, 기존 위젯 ID·배치를 새 renderer로 갱신    |

SDK 58의 expo-widgets changelog에서 Android 구현 추가를 확인했다. 현재 설치 버전은 58.0.10이며 Android widget 구성은 공식 구현을 기준으로 옮겼다. [Expo widgets 공식 changelog](https://github.com/expo/expo/blob/main/packages/expo-widgets/CHANGELOG.md)

Widget 함수는 앱의 hook/context를 읽는 화면이 아니다. isolated renderer는 순수한 snapshot을 받고 필요한 디자인·포맷 결과를 명시적으로 사용한다. 앱이 아닌 widget 런타임에서 네트워크나 임의 모듈 의존성을 실행하지 않도록 경계를 둔다. config plugin 변화는 개발 native build가 필요하다. [Expo widgets 공식 SDK 문서](https://docs.expo.dev/versions/v58.0.0/sdk/widgets/)

Android 전체 위젯 탭의 앱 열기는 설치한 58.0.10에서 필요한 작은 버전 한정 패치로 연결했다. `opensApp`일 때 Glance modifier에 package launch intent를 연결한다. 존재하지 않는 공식 JavaScript deep-link API를 선언하거나 앱 자체 native module을 다시 만들지 않는다. 전체 widget tap은 앱 시작 동작이며 Todo 상세 deep link로 설명하지 않는다. 기존 Android 위젯 host 보존·새 props 갱신은 전용 에뮬레이터에서 확인했고 OEM launcher는 별도 release QA 범위다.

색상·정렬·진행률·빈 상태는 기존 Aido 톤과 iOS 디자인 의미를 따른다. iOS의 SwiftUI와 Android의 Compose/Glance는 같은 렌더링 엔진이 아니므로 pixel 단위 동일 출력이나 Liquid Glass의 Android 재현을 완료 조건으로 삼지 않는다. 각 플랫폼에서 가독성, touch target, 글자 배율, 크기별 잘림과 사용자 데이터 격리를 검증한다.

### 기존 Android 설치의 실제 업그레이드 검증

원본 worktree에서 확보한 1.8.0 APK와 별도 emulator 복제본으로 기존 위젯 세 개를 등록한 뒤, 새 APK를 `install -r`로 설치했다. 기존 receiver 이름 `AidoTodaySummary/List/Large`와 host ID 3/4/5를 보존하는 최소 shim만 남기고 새 SDK Glance renderer에 전달한다. 기존 MMKV snapshot은 읽기 전용으로 이관하며 fresh SDK props가 존재하면 덮어쓰지 않는다.

실제 RemoteViews에서 세 크기의 제목·개수·빈/손상 데이터 fallback을 확인했다. 기존 MMKV data/CRC SHA가 유지됐고 50회 동시 갱신 경쟁에서 fresh 계정/logout props를 과거 snapshot으로 덮어쓴 경우는 0회였다. 이 결과는 Android 이전 위젯 host 유지 근거이며 이전 iOS binary 전체 기능 검증과 동일한 결과로 표현하지 않는다.

production widget TypeScript/TSX는 **22 files / 1,685 lines → 14 files / 1,026 lines**다. 테스트와 factory를 제외한 같은 범위를 비교했다. Android 호환 native shim/plugin은 **274 lines**를 별도로 집계한다. 파일 감소가 native 호환 코드를 포함한 전체 성능 개선을 뜻하지 않는다.

### NativeTabs와 Liquid Glass

Feed/Memo/Mypage 세 탭은 `expo-router/native-tabs`로 이동했다. 직접 측정한 JS tab-height context와 legacy 높이 보정을 제거하고 화면 safe area와 시스템 탭 동작에 맞춘다. Memo FAB는 시스템 하단 영역과 겹치지 않는 간격을 유지한다. Friend는 기존 상세/목록 route 역할을 유지한다.

iOS 26 이상의 시스템 탭 배경·glass 동작은 OS가 제공한다. Android는 플랫폼의 native tab 표현을 사용한다. iOS 전용 배경/blur prop을 모든 OS에서 동일 효과가 있는 것으로 가정하지 않는다. [Expo NativeTabs 플랫폼별 prop 문서](https://docs.expo.dev/versions/v58.0.0/sdk/router/native-tabs/)

## 5. 버전·EAS·OTA와 하위 호환

Before:

```ts
const VERSION = '1.9.1';
```

After `apps/mobile/app.config.ts`:

```ts
import { version } from './package.json';

const VERSION = version;
```

수동 조회의 순수 옵션:

```ts
export function getAppVersionQueryOptions(service: AppVersionService) {
  return queryOptions({
    queryKey: ['app-version', 'config'] as const,
    queryFn: ({ signal }) => service.getConfig(signal),
    retry: false,
    staleTime: 0,
  });
}
```

마이페이지에서 사용자가 확인을 누를 때만 조회한다. 빌드 중 package version이 아니라 설치된 `Application.nativeApplicationVersion`으로 플랫폼별 최신 버전을 비교한다. 이전 설치 버전이면 기존 store gateway를 열고, 같거나 더 새 버전이면 확인 dialog를 표시한다. 잘못된 JSON·disabled config·알 수 없는 플랫폼/버전·네트워크 실패는 기존 실패 안내를 사용한다. Expo Go/web 등 설치 metadata가 없는 환경에는 이 기능을 노출하지 않는다.

`runtimeVersion: { policy: 'fingerprint' }`, EAS `appVersionSource: remote`와 `autoIncrement: true`는 **기존 운영 정책을 유지**했다. fingerprint는 이번에 새로 도입한 정책이 아니다. SDK·native dependency·widget plugin 변화가 있는 이번 업데이트는 새 native binary를 먼저 검증한다. package의 1.10.0이라는 값만으로 기존 설치와 OTA가 호환된다고 판단하지 않는다. [Expo runtimeVersion 공식 문서](https://docs.expo.dev/eas-update/runtime-versions/)

하위 호환은 REST 입력/응답과 공개 schema hash, secure storage·인증 refresh, cache prefix, 설정 저장, 설치 버전 판정과 데이터 노출 경계에서 유지한다. 실제 기존 Android 1.8.0 APK의 위젯 3종은 새 APK 설치 후 component identity·host ID가 유지되고 앱을 열기 전에 새 renderer로 표시되는 것을 검증했다. OEM launcher·스토어 release signing 조합의 검증은 별도다. 제거한 legacy 코드의 파일 수만으로 사용자 migration 완료를 주장하지 않는다.

### 이전 앱 → 새 API의 별도 배포 gate

기존 앱 사용자는 서버 배포 직후 앱을 업데이트하지 않을 수 있다. **1.10.0 앱 → 새 API가 정상이어도 이전 앱 → 새 API 검증이 끝난 것은 아니다.** 서버 배포의 완료 조건에 이 조합을 별도로 둔다.

| 경계                          | 근거                                                                                                        | 상태                                                   |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 배포된 1.7.x·1.8.2 OpenAPI    | 고정된 released fixture의 schema/path fingerprint 불변 검사                                                 | 기존 전체 E2E 검증에서 통과                            |
| Zod 최신화                    | 4.6 후보에서 공개 fingerprint 변화 발견, stable 4.3.6 유지                                                  | 구현 완료                                              |
| 이전 앱의 실제 HTTP 소비 형태 | 현재 validator를 재사용하지 않는 고정 legacy payload schema로 인증·todo·날짜·cursor·notification·error 검증 | 추가 회귀 테스트 구현, 실행 결과 확인 대기             |
| 1.9 댓글 payload              | parentId/items/clientRequestId와 기존 conversation 읽기 shape                                               | 추가 회귀 테스트 구현, 실행 결과 확인 대기             |
| app-version                   | 기존 `v1/app-config/app-version` 경로와 수동 확인 유지, 기존 endpoint에 새로운 필수 입력 추가 없음          | 코드 경계 검토 완료, 이전 설치에서 실제 요청 확인 대기 |
| DB migration                  | 기준 대비 Prisma schema 변화는 generator `moduleFormat: cjs → esm`, SQL migration 추가·변경 없음            | 정적 diff 확인 완료                                    |
| DB 실행 호환성                | 새 migration/runtime image로 기존 데이터 읽기·쓰기와 실제 migrate deploy                                    | Docker 실행 검증 대기                                  |
| 배포된 앱 binary              | 이전 설치 그대로 새 API에 연결해 login/refresh·CRUD·알림·댓글·오류 흐름 확인                                | 실제 기기 검증 대기                                    |

`apps/api/test/e2e/legacy-client-compatibility.e2e-spec.ts`는 최신 공유 validator를 가져와 이전 계약을 새 정의로 덮어쓰지 않는다. 이전 소비 필드를 고정한 schema와 실제 HTTP 요청으로 수신 응답을 검증한다. 버전 label만 다르게 실행하는 테스트는 해당 버전 binary 자체를 실행한 결과가 아니므로 기기 gate를 대체하지 않는다.

공개 fingerprint 보존은 계약 변화 탐지이고, HTTP 회귀는 실제 validation·serialization·status code 확인이며, 이전 binary 검증은 native 설치·인증 저장소·소비 코드 확인이다. 세 결과를 구분해 PR과 배포 기록에 남긴다. 기존 SQL migration을 다시 쓰거나 구 앱이 사용하는 DB 필드·REST 필드를 제거하지 않는다.

## 6. Catalog·불필요한 의존성·Dependabot

공통 라이브러리는 기본 catalog, Expo native cohort는 `expo58`, Nest cohort는 `nest12`에서 관리한다. CLI가 기대하는 Expo native 버전은 공식 install/check 결과와 실제 peer/type/native 빌드로 대조한다. Nest core/testing/config/swagger 관련 Dependabot PR도 독립 merge 대신 같은 호환 묶음으로 반영했다. 기존 PR을 살펴본 것과 해당 PR을 실제 merge한 것은 구분한다.

사용하지 않는 내부 debounce/throttle wrapper만 남아 있던 `packages/utils`와 API/mobile 의존성, 미사용 공유 `tooling/jest` preset을 제거했다. API의 Jest/ts-jest 및 nestjs-zod 경로는 Vitest/native Standard Schema로 정리했다. 모바일의 실제 Jest/jest-expo와 테스트에 필요한 peer는 유지한다. 사용 여부를 확인하지 않은 의존성을 이름만 보고 지우지 않는다.

`.npmrc`는 `strict-peer-dependencies=true`를 사용한다. `pnpm install --frozen-lockfile` 검증이 통과했고 native 호환 예외는 위의 버전 한정 patch/hook으로 추적한다. 전체 peer 규칙을 느슨하게 바꿔 설치만 성공시키지 않는다.

## 7. Docker·ignore·Turbo와 실행 경계

### Docker Before → After

| 경계                 | Before                                         | After                                                               |
| -------------------- | ---------------------------------------------- | ------------------------------------------------------------------- |
| 빌드 dependency 입력 | API와 미사용 공유 package manifest를 수동 열거 | root의 Turbo 버전으로 workspace prune                               |
| lockfile             | 전체 workspace lockfile                        | API/migration 각각의 prune 결과 lockfile                            |

| runtime              | API production dependency                      | 배포 산출물·production dependency만, non-root, bootstrap entrypoint |
| migration runtime    | image build 과정에서 동적 dependency 해결      | 최소 Prisma/pg-boss와 migration 파일만, non-root                    |

이전 migration dependency 설치:

```dockerfile
RUN pnpm init && pnpm add prisma@7.10.0 pg-boss@12.27.0
```

변경 후의 핵심 흐름은 pruner가 만든 json과 lockfile을 먼저 사용하고 source를 뒤에 복사하는 것이다. API와 migration을 별도로 prune한다.

```dockerfile
RUN pnpm dlx "turbo@$(node -p 'require("./package.json").devDependencies.turbo')" prune @aido/api --docker --out-dir out/api
```

실제 stage는 `.pnpmfile.cjs`, `.npmrc`와 필요한 patch도 함께 소비한다. API production 배포는 `pnpm --filter @aido/api deploy --legacy --prod /app/production`, 실행은 `node --max-old-space-size=384 dist/src/bootstrap.js`다. migration workspace는 Prisma 7.10.0/pg-boss 12.27.0과 migration script를 포함하며 이미지 빌드 시 DB migration을 수행하지 않는다.

최종 production과 migration은 UID 1001의 전용 사용자로 실행한다. RDS CA 인증서를 읽을 수 있는 권한과 migration URL guard를 유지한다. dev dependency·모바일 소스·테스트·coverage·문서·`.claude`·로컬 env와 secret·native build 산출물이 production context/배포물에 불필요하게 들어가지 않도록 `.dockerignore`, `.gitignore`, package files를 함께 검토했다. 설치에 필요한 workspace 설정과 patch는 제외하지 않는다.

두 이미지 **빌드 성공**과 실제 실행 성공은 구분한다. 아래 runtime 체크에서 DB 접속·migration·health·SIGTERM·권한·최종 파일 내용을 확인한다. 동일 조건의 이전 이미지 크기 측정이 없어 용량 감소율은 기재하지 않는다.

### 실제 런타임 파일과 용량 검사

production 이미지의 `.pnpm` 내부를 포함해 조사하니 Prisma 선택적 peer가 CLI와 PGlite 개발용 graph를 함께 배포하고 있었다. `@nestjs-cls/transactional-adapter-prisma@2.0.1>prisma` peer만 scoped override로 제거하고, client 7.10.0의 CLI/TypeScript 선택적 peer는 version-scoped readPackage에서 제외한다. API의 직접 dev CLI와 migration workspace의 직접 production CLI는 유지한다. optional dependency 전체를 끄거나 이미지에서 vendor 파일을 임의 삭제하지 않는다.

```js
if (pkg.name === '@prisma/client' && pkg.version === '7.10.0') {
  delete pkg.peerDependencies.prisma;
  delete pkg.peerDependencies.typescript;
  delete pkg.peerDependenciesMeta.prisma;
  delete pkg.peerDependenciesMeta.typescript;
}
```

동일 1.10 source의 패키징 변경 전 **221,398,359 bytes**, 변경 후 **156,198,678 bytes**로 약 **29.4%** 줄었다. 출시 전 원본 이미지와 같은 조건의 benchmark가 아니라 최종 runtime dependency 분리 전후 수치다. production image에서 CLI/PGlite graph·앱 소스·모바일·테스트·env 파일이 없고 생성된 Prisma/CLS adapter import, UID1001·CA 읽기, 실제 DB/queue health를 확인했다. 종료는 SIGTERM을 받고 exit0이었다.

런타임 smoke는 production stage 산출물을 **local development/mock 설정**으로 실행했다. NODE_ENV=production에 실제 OAuth/email 설정이 없는 실행은 기존 guard가 올바르게 거부했다. 운영 secret 없이 fake provider를 성공 연결로 주장하거나 guard를 완화하지 않았다. 최종 migration stage는 non-root로 실제 migrate deploy와 queue schema37 검증을 통과했다.

## 8. 테스트 전환과 flake 검증

API Vitest는 unit/integration/e2e project를 분리한다. Nest의 legacy decorator와 metadata를 SWC 설정으로 유지하고 unit은 제한된 병렬 worker, DB project는 fileParallelism=false/maxWorkers=1을 사용한다. setup/teardown에서 격리된 test database와 resource 수명을 관리하고 clearMocks/restoreMocks와 seed shuffle로 순서 의존성을 점검한다.

모바일은 공식 jest-expo와 Reanimated Jest 환경을 유지한다. 새 native Toolbar/Glass 등 native view 경계만 mock하고 HeroUI provider/component의 실제 조합은 테스트한다. 테스트 provider에만 animation disable 설정을 주어 web Jest 환경의 DOM layout animation 의존성을 제거했다. production 애니메이션을 끄지 않았다.

### 실제 앱 실행에서 발견한 회귀와 수정

iOS 이메일 로그인 진입에서 `ErrorBoundaryContext not found`를 확인했다. 폼의 예상하지 못한 비동기 오류 전달을 위해 추가한 useErrorBoundary 위에 해당 라이브러리 context가 없었다. Expo Router의 route ErrorBoundary export와 react-error-boundary context를 같은 것으로 볼 수 없다. 최초 route 상위 수정 뒤 실제 Todo overlay에서 같은 오류가 발생했으므로, 최종 구조는 **QueryErrorBoundary → OverlayProvider → AuthGateLayout**으로 배치한다. OverlayProvider가 children과 별도의 sibling으로 마운트하는 sheet에도 context를 전달한다. 제출 showBoundary와 실제 overlay open 흐름이 fallback·기존 ErrorReporter에 전달되는 회귀 테스트를 추가했다. 이 수정 이후의 전체 suite 집계는 기존 반복 집계와 구분해 갱신한다.

인증 완료 뒤 `/`가 unmatched route로 남는 회귀도 실제 가입 흐름에서 발견했다. root index를 미인증 Protected 그룹에만 두어 인증 상태 변경 때 index가 사라졌고, NativeTabs에는 feed/memo/mypage만 있어 `/` 화면이 없었다. root index를 항상 등록하고 loading/locked → `/loading`, authenticated → `/feed`, unauthenticated → `/login`으로 선언적 Redirect한다. SDK 58의 Protected redirectTo는 `/`를 명시한다. Stack은 항상 mount하며 기존 cold-start notification navigation을 유지하고 login/signup mutation에 별도 imperative 이동을 추가하지 않는다. [Expo Protected 공식 문서](https://docs.expo.dev/router/advanced/protected/)

실제 iOS·Android 화면에서 흰 버튼/흰 toast 문구만 보이는 색상 회귀도 확인했다. 기존 팔레트 값은 변경되지 않았지만 Uniwind 1.12의 native compiler에서 `@layer theme` 바로 아래의 light/dark variant가 앱의 custom token scope로 연결되지 않았다. --main·--gray-8이 unset으로 평가되어 배경이 사라졌다. 기존 선언을 `:root` 안으로 옮겨 값은 그대로 유지했다. 공식 구조도 root 아래의 theme variant를 사용한다. [HeroUI Native 공식 theming 설명](https://heroui.com/en/blog/styling-and-theming-in-heroui-native)

```css
@layer theme {
  :root {
    @variant light {
      --main: oklch(0.702 0.1919 35);
    }
    @variant dark {
      --main: oklch(0.702 0.1919 35);
    }
  }
}
```

실제 설치된 native compiler로 iOS/Android × light/dark 네 조합의 각 27개 앱 토큰을 기준 팔레트와 대조했다. 선언 변경 0건, unresolved 0건이며 결과는 `/tmp/aido-theme-token-audit.json`에 남겼다. 이는 기존 색상 복구 근거이며 새로운 브랜드 팔레트 도입이 아니다. 실제 기기에서 버튼·toast·field·surface·border·선택 상태의 light/dark 화면을 추가 확인한다. React Native style mock만 사용하는 unit test 통과로 이 검증을 대신하지 않는다.

settings 폴더의 재사용 IconRadioItem도 route 밖 shared/ui로 옮겨 default export가 없는 파일을 route로 해석하는 Metro 경고를 제거했다. 원본 RadioGroup.Item props를 확장하며 테마 판정은 unchecked cast 대신 boolean type guard를 사용한다.

기준 모바일 테스트는 모든 assertion이 통과했지만 Jest가 open-handle 경고와 함께 종료하지 않았다. QueryClient cancel/clear, provider unmount와 timer cleanup을 보완했고 변경 후 반복 실행은 정상 종료했다. `forceExit`로 문제를 감추지 않았다. 임의 sleep을 늘려 race를 통과시키는 방식 대신 상태·작업 완료와 cleanup을 검증한다.

현재 `toMemoConversionInput`은 상위 폼의 검증된 값에서 기존 공유 요청 schema를 만든다:

```ts
export function toMemoConversionInput(data: AddTodoFormInput): ConvertMemoToTodosInput {
  return convertMemoToTodosSchema.parse({
    todos: [
      {
        title: data.title,
        categoryId: data.categoryId,
        startDate: formatDate(data.startDate),
        endDate: data.endDate ? formatDate(data.endDate) : undefined,
        scheduledTime: data.isAllDay ? undefined : (data.scheduledTime ?? undefined),
        isAllDay: data.isAllDay,
        visibility: data.visibility,
        isRecurring: data.isRecurring,
        recurrence:
          data.isRecurring && data.repeatEndDate
            ? { daysOfWeek: data.daysOfWeek, endDate: formatDate(data.repeatEndDate) }
            : undefined,
      },
    ],
  });
}
```

메모 mutation의 이전 `onSettled`는 invalidate를 시작하지만 완료 Promise를 반환하지 않았다. 상세 화면이 다시 mount할 때 cache에 이전 내용이 남을 수 있었다. 변경 후 mutation 완료 경계는 다음과 같다:

```ts
onSuccess: async (memo, { memoId }) => {
  await queryClient.cancelQueries({ queryKey: MEMO_QUERY_KEYS.detail(memoId) });
  queryClient.setQueryData(MEMO_QUERY_KEYS.detail(memoId), memo);
  trackEvent('memo_updated', { memo_id: memoId });
  queryClient.removeQueries({ queryKey: AI_QUERY_KEYS.parseMemo(memoId) });
},
onSettled: (_, __, { memoId }) => Promise.all([
  queryClient.invalidateQueries({ queryKey: MEMO_QUERY_KEYS.list() }),
  queryClient.invalidateQueries({ queryKey: MEMO_QUERY_KEYS.detail(memoId) }),
]),
```

폼이 열린 상태에서 조회 응답마다 reset하는 effect를 추가하지 않는다. 그것은 작성 중인 값을 덮어쓸 수 있기 때문이다. 서버 상태의 mutation 경계에서 cache를 최신화하고 부모 폼의 작성 상태는 그대로 부모가 관리한다.

반복 생성의 이전 코드는 `createMany` 결과를 즉시 반환했다. 변경 후 기존 repository와 transaction 안에서 occurrence별 checklist를 저장한다:

```ts
const todos = await this.todoRepository.createMany(items, recurrenceGroupId);
if (data.items?.length) {
  for (const todo of todos) {
    await this.todoRepository.createInlineItems(todo.getId().getValue(), data.items);
  }
}
return todos;
```

실제 PostgreSQL E2E에서 두 occurrence가 각각 `우유`, `계란`을 갖고 네 item ID가 독립적이며 첫 occurrence 완료가 둘째 occurrence에 영향을 주지 않는 것을 확인했다. 변경 전 기대 실패와 변경 후 unit11cases·관련 E2E46cases·Todo E2E58cases·seed1301/1302/1303 통과를 보존했다. 최종 전체 테스트는 이 추가 회귀를 포함해 별도 집계한다.

설치 metadata는 Expo Go 여부와 설치된 native 버전을 서로 다른 개념으로 처리한다:

```ts
if (
  Constants.executionEnvironment === ExecutionEnvironment.StoreClient ||
  (Platform.OS !== 'ios' && Platform.OS !== 'android')

  return undefined;
}
return {
  platform: Platform.OS,

```

실제 SDK58 dev binary에서 executionEnvironment는 bare, expoVersion은 undefined, nativeApplicationVersion은 1.10.0이었다. 마이페이지 행 노출과 disabled 개발 정책의 기존 실패 안내를 확인했다. production 최신 버전·store 이동 성공은 이 결과로 대신하지 않는다. [Expo Constants 공식 API](https://docs.expo.dev/versions/v58.0.0/sdk/constants/)

## 9. 마지막 stack만 무거운 CI 실행

중간 PR의 CI를 생략할 때도 마지막 PR에서 모든 누적 변경을 검증해야 한다. `stack:1.10.0`과 마지막 PR의 `ci:stack-tip` label, `upgrade/1.10-` branch chain을 검사한다. 같은 저장소의 열린 stack이 develop까지 연결되어 있어야 하고 순환·연결 누락·중복 tip·여러 tip은 gate에서 실패한다.

| 대상                             | CI 동작                              |
| -------------------------------- | ------------------------------------ |
| 중간 stack PR·draft              | 가벼운 정책 검사, 무거운 테스트 생략 |
| 유효한 마지막 non-draft PR       | develop 기준 전체 누적 변경 검사     |
| 일반 PR                          | 일반 비교 기준 검사                  |
| main/develop push·수동 실행      | 전체 검증                            |
| 오래된 workflow와 PR head 불일치 | stale head gate 실패                 |

마지막 PR의 바로 이전 branch만 비교하면 앞 단계 변경이 affected 범위에서 빠질 수 있으므로 최종 gate는 develop과 현재 tip의 누적 범위를 사용한다. ancestor head가 tip에 포함되었는지 GitHub API 비교도 확인한다. `concurrency`의 cancel-in-progress는 낡은 같은 branch 실행을 취소한다.

정적 검사는 전체 repository에서 실행하고 typecheck/test는 검증된 affected 범위를 사용한다. API unit과 coverage의 중복 실행은 줄이고 API 영향이 있을 때 integration/e2e를 수행한다. 실패 로그는 artifact로 남기면서 tee 뒤의 실제 test exit code를 보존한다. workflow action은 full SHA로 고정한다.

커밋은 Conventional Commits와 저장소 규칙을 따르고 공유 계약/의존성 → API → 클라이언트 기반/feature → native → 검증/문서 순서로 리뷰 가능한 layer를 만든다. gh-stack으로 부모 관계를 유지하고 마지막 tip만 누적 CI를 실행한다. stack 생성·PR 게시·merge·배포 여부는 실제 실행 후 별도로 기록한다. 이 문서 작성 시 PR 번호나 merge 완료를 가정하지 않는다.

PR에는 문제와 결과 동작, 주요 Before/After, 호환 제약, 실제 검증 명령·case 수·미완료 항목을 먼저 적는다. 면접관·reviewer가 대화 내용을 몰라도 판단할 수 있도록 구현 이유와 증거를 설명하고 검증되지 않은 개선율은 쓰지 않는다.

## 11. 재검증 명령과 기록 방법

루트 정적 검사는 사용자 지침의 순서를 유지한다.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm --filter @aido/api build
pnpm --filter @aido/mobile typecheck
```

API seed 검증 예:

```sh
pnpm --filter @aido/api exec vitest run --project unit --sequence.shuffle --sequence.seed=101
pnpm --filter @aido/api exec vitest run --project integration --sequence.shuffle --sequence.seed=101
pnpm --filter @aido/api exec vitest run --project e2e --sequence.shuffle --sequence.seed=101
```

모바일 seed 검증 예:

```sh
pnpm --filter @aido/mobile exec jest --runInBand --randomize --seed=5812
```

모듈 그래프는 tests/assets를 제외하고 실제 TypeScript resolution을 사용한다. 예를 들어 모바일:

```sh
npx --yes madge@8.0.0 --circular --extensions ts,tsx --ts-config apps/mobile/tsconfig.json --exclude '(^|/)(__tests__|assets)/|\.(spec|test)\.' apps/mobile/src apps/mobile/app --json
```

결과에는 commit/head, lockfile 상태, runner 버전, seed, suite/case 수, exit code, duration, cache 조건과 실패 로그를 남긴다. 수치가 바뀌면 새 실행 근거와 함께 이 문서·PR 검증 표를 갱신한다. 배포 전 대기 항목은 실제 실행 결과가 있을 때만 완료로 전환한다.
